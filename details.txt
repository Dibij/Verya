You are building a developer tool called **Verya**.

Tagline:

**Verya — Visual editing for real code.**

The goal is to build a tool that combines the best parts of:

* a terminal developer tool
* a live frontend previewer
* a visual UI editor
* a lightweight design system editor
* an AI-assisted coding environment

But there is one principle above everything else:

**THE SOURCE CODE IS THE SOURCE OF TRUTH.**

Verya must not create a fake visual representation that only exists inside its own editor.

When a user visually changes something, Verya must translate that change back into the user's actual source files.

The user should be able to close Verya, open the project in VS Code, inspect the source files, and see the exact UI changes there.

The user should also be able to edit the source manually and have Verya reflect those changes in the visual preview.

This is fundamentally a:

**CODE ↔ VISUAL UI**

system.

==================================================

1. PRODUCT CONCEPT
   ==================================================

Verya is a local developer tool that allows a user to point the application at an existing frontend project and visually edit the actual UI.

Example:

```bash
Verya ./src/App.tsx
```

or:

```bash
Verya ./my-project
```

Verya launches a visual development environment.

The user sees:

* source code
* component tree
* live rendered UI
* properties/design controls
* assets
* design systems/templates
* terminal/build status
* optional AI assistant

The user can visually interact with the UI and modify:

* position
* size
* spacing
* alignment
* colors
* gradients
* backgrounds
* borders
* border radius
* shadows
* opacity
* typography
* images
* icons
* visibility
* layout structure
* flex/grid properties
* responsive behavior
* component styles
* component hierarchy

Those modifications must be reflected back into the underlying source code.

==================================================
2. FIRST MVP
============

Do NOT attempt to support every framework initially.

The first MVP should focus on:

**React + TypeScript + TSX**

The tool should be able to load a standard frontend project containing things such as:

```text
src/
  App.tsx
  components/
  pages/
  styles/
  assets/
package.json
```

Support common styling approaches where practical, especially:

* CSS
* CSS modules
* Tailwind CSS
* inline styles

Do not create an unnecessarily large abstraction layer for every CSS framework.

Build the architecture so other frameworks can be added later.

Potential future support:

* JSX
* Vue
* Svelte
* HTML/CSS
* React Native
* other component-based UI systems

But React + TSX is the MVP.

==================================================
3. SOURCE CODE MUST REMAIN REAL
===============================

This is the most important requirement.

Never treat the rendered preview as the canonical representation.

The canonical representation is:

```text
actual source files
```

The preview is disposable.

The internal editor model is also not authoritative.

The system should conceptually work like:

```text
SOURCE FILE
     ↓
Parser / AST
     ↓
Component Understanding
     ↓
Live Runtime
     ↓
Visual Canvas
```

And when the user makes a visual modification:

```text
Visual Change
     ↓
Semantic Layout/Style Operation
     ↓
AST / Source Transformation
     ↓
Formatted Source File
     ↓
Save
     ↓
Live Preview Update
```

Do not solve this primarily with crude string replacement.

Use an AST/code transformation approach where appropriate.

The generated source should remain:

* readable
* formatted
* idiomatic
* maintainable
* structurally similar to the original code

Do not destroy the developer's code just because the visual editor is easier to implement that way.

==================================================
4. BIDIRECTIONAL EDITING
========================

Verya must support two directions.

### Code → UI

When the user edits:

```tsx
<div className="p-4 rounded-xl">
```

the visual canvas updates.

### UI → Code

When the user selects that element and changes:

```text
Padding: 16px → 24px
Radius: 12px → 20px
```

Verya updates the underlying TSX/CSS.

This synchronization should happen continuously or with an obvious save/apply action depending on the implementation.

The user should never have to manually recreate visual changes in code.

The center of Verya should be the rendered application.

It must support:

* selecting elements
* hover outlines
* visual selection state
* nested component selection
* click-to-select
* drag interactions
* resize handles
* responsive preview sizes

When an element is selected, show a subtle visual outline and handles.

Example:


7. COMPONENT TREE
=================

Create a component hierarchy panel.

Example:

```text
App
```

==================================================
8. VISUAL EDITING
=================

The user should be able to select an element and directly modify its visual properties.

Support:

### Layout

* display
* width
* height
* min/max width
* min/max height
* margin
* padding
* gap
* alignment
* justification
* flex direction
* grid structure
* positioning

### Position

Allow drag interactions.

BUT:

Do not automatically destroy responsive layouts by converting everything into absolute positioning.

The editor must understand the existing layout model.

For example:

If an element is in Flexbox, prefer modifying:

* gap
* margin
* alignment
* order
* padding

If an element is in Grid, prefer:

* grid placement
* gap
* alignment

Only use absolute coordinates when the layout genuinely calls for absolute positioning.

The goal is:

**visual freedom without generating garbage CSS.**

==================================================
9. RESPONSIVE DESIGN
====================

The visual editor must understand responsive layouts.

Provide preview sizes such as:

* Mobile
* Tablet
* Desktop
* Custom width

Allow the user to inspect the UI at different widths.

Do not make changes that only look correct at one arbitrary screen size.

When a property is changed, Verya should understand whether it belongs to:

* base styles
* mobile breakpoint
* tablet breakpoint
* desktop breakpoint

Where possible, expose responsive controls.

For example:

```text
Width

Desktop: 420px
Tablet: 360px
Mobile: 100%
```

The actual implementation may use appropriate media queries/classes.

==================================================
10. DESIGN SYSTEMS / TEMPLATES
==============================

One of Verya's major features should be reusable visual design systems.

Do NOT treat a template as a screenshot or a static page.

A template is a coordinated set of visual rules.

Examples:

* Glassmorphism
* Liquid Glass
* Minimal
* Dark Premium
* Neo Brutalism
* Soft UI
* Cyberpunk
* Editorial
* Material-inspired
* Gradient
* Clean SaaS

The first important template should be:

# GLASSMORPHISM

Applying the Glassmorphism system should modify the existing interface intelligently.

Do not replace the entire application.

Instead analyze existing components and apply the visual language.

Glassmorphism should influence:

* surfaces
* cards
* buttons
* navigation
* dialogs
* inputs
* borders
* shadows
* background gradients
* typography hierarchy
* spacing
* decorative lighting

A glassmorphism system may include:

```text
dark atmospheric background
translucent surfaces
backdrop blur
subtle borders
large corner radius
soft depth
background glow
controlled accent colors
```

The user should be able to customize the system.

For example:

```text
Glassmorphism

Surface opacity       12%
Blur                   20px
Border opacity          18%
Corner radius           24px
Shadow                  Soft
Accent                 Orange
Background             Dark
```

Changing the design system values should update the actual UI.

17. DRAGGING AND RESIZING
=========================

The user must be able to visually drag elements.

Example:

Drag downward.

Do not simply write:

```css

left: 421px;
```

unless the component actually uses absolute positioning.

The objective is:

**Figma-like manipulation with developer-quality source output.**

Likewise, resizing should intelligently map to:

* width
* max-width
* flex-basis
* grid columns
* padding
* font size

depending on context.

* redo

25. ERROR HANDLING

==================================================
28. PERFORMANCE
===============

The preview must feel fast.

Do not repeatedly rebuild the entire application when unnecessary.

Use incremental updates where possible.

Avoid memory leaks.

Do not hold unnecessary copies of large projects in memory.

Images should not cause uncontrolled memory usage.

==================================================
29. SECURITY / PROJECT SAFETY
=============================

Because Verya operates directly on real files, treat file modification as a high-risk operation.

Before making major transformations:

* know exactly which files will change
* avoid unrelated files
* create safe backups/checkpoints where appropriate
* make changes atomic where possible

Never overwrite arbitrary project files without understanding them.

Do not execute arbitrary project commands without the user's explicit context/intent.

34. EXAMPLE
===========

Given:

```tsx
export default function App() {
  return (
    <main className="p-4">
      <section className="card">
        <h1>Hello</h1>
        <button>Start</button>
      </section>
    </main>
  );
}
```

The user selects the card.

They choose:

```text
Template: Glassmorphism
Radius: 24px
Padding: 32px
Blur: 20px
Background: translucent
```

Verya modifies the actual implementation.

The exact syntax can depend on the project's styling system, but it should result in legitimate developer-readable source.

Then the user drags the button lower.

Verya should choose an appropriate layout-level modification rather than blindly introducing absolute positioning.

==================================================
36. MOST IMPORTANT IMPLEMENTATION RULE
======================================

Whenever you have to choose between:

A visually impressive implementation that generates terrible code

and

A slightly less magical implementation that preserves clean source code

CHOOSE THE SECOND.

The defining quality of Verya is:

**visual editing without sacrificing real code.**

The user must be able to trust the resulting source.

==================================================
37. FINAL ACCEPTANCE CRITERIA
=============================

The MVP is successful only if I can:

1. Open a React/TypeScript project from the terminal.

2. See the actual application rendered live.

3. Select an element visually.

4. See its relationship to the actual source/component.

5. Change visual properties from the UI.

6. See the preview update.

7. See the actual TSX/CSS source update.

8. Edit the source manually.

9. See the visual preview update.

10. Drag an element while preserving a sensible responsive layout.

11. Change a background color.

12. Replace an image.

13. Apply a Glassmorphism design system.

14. Undo the changes.

15. Save the project.

16. Open the same project in another editor and see the resulting source code.

If these work reliably, Verya has achieved its core purpose.

Everything else is secondary.
